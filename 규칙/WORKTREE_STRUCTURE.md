## 이후 작업의 논리 구조

```text
PM 통합 워크트리
├── 기능 작업 워크트리       페이지·UI·서비스별 변경
├── 자산 작업 워크트리       이미지·출처·사용 위치 관리
├── 검토 작업 워크트리       PC·모바일·접근성·콘텐츠 검토
└── janiter 작업 워크트리    불필요 파일·중복·경로 정리
```

각 작업 공간은 필요할 때 오르카로 만들며 고정된 수의 세션을 항상 실행하지 않는다. PM은 통합 기준 커밋을 정하고 작업마다 담당 에이전트를 선정한다. 이미 검증된 `570ceab` 기반 변경은 해당 커밋을 포함하는 작업 공간에서 시작한다. `user4`가 최신 구현을 포함한다고 가정하지 않는다.

기존 시안을 이어서 수정할 때는 PM이 현재 통합 브랜치를 명시적으로 기준으로 지정한다. 독립 작업의 기본 브랜치 생성과 현재 구현 기반의 후속 작업을 구분한다. `--parent-worktree`는 오르카 계보이고 Git 기준 커밋 지정과는 별개다. 실제 CLI의 버전별 가이드와 도움말을 확인하여 두 기준을 모두 맞춘다.

## 파일 소유 범위

| 담당 | 허용 범위 | 조정이 필요한 범위 |
| --- | --- | --- |
| PM | 공통 규칙, 기준 커밋, 통합, 빌드 연결 | 작업 세션과 동일 파일을 동시에 수정하지 않음 |
| 기능 작업 | 배정된 모듈·CSS·JS 및 관련 검증 | 공통 헤더·푸터·빌드·package.json 변경은 PM과 조정 |
| 자산 작업 | `assets/images/`, 사용 위치·출처 기록 | 기존 참조 이미지를 교체할 때 소비 코드와 함께 조정 |
| 검토 작업 | 검토 결과와 재현 근거 | 수정이 필요하면 별도 수정 범위를 배정받음 |
| janiter | PM이 지정한 정리 대상과 정리 기록 | 삭제·대량 이동 전 참조와 실제 사용 여부 확인 |

`dist/`는 빌드 산출물을 포함하지만 기존 프로젝트의 일부 원본 자산도 `dist/assets/`에 있다. 산출물이라는 이유만으로 폴더를 비우거나 삭제하지 않는다. 생성 HTML은 원본 모듈 수정 후 다시 생성한다.

## 현재 일반 폴더와 터미널

```text
Myung_Project_Test/
├── 규칙/                  공통 규칙·진행·인계·작업 배정
├── assets/images/         새 이미지 원본 저장
├── janiter/               정리 작업용 일반 폴더
├── source-code/           소스 작성용으로 마련한 일반 폴더
├── *.mjs                  현재 실제 소스 모듈
└── dist/                  기존 자산과 생성 웹 화면
```

`janiter`와 `소스코드 작성` 터미널은 각각 일반 폴더에서 시작하는 PowerShell 탭이다. 에이전트나 독립 워크트리는 아직 아니다. 기존 루트 소스를 `source-code/`로 자동 이동하지 않는다. 구조 변경 작업을 별도로 배정하고 import·자산·빌드 경로를 함께 검증한다.

## 통합 흐름

작업 배정 → 별도 워크트리 확인 → 구현과 자체 검증 → 산출물 커밋 → 다른 세션의 교차 검토 → PM 검토 → PM 통합 → 통합 빌드와 브라우저 검증 → 기록 갱신 순서로 진행한다.

PM은 커밋별 포함 파일을 검토한 뒤 통합한다. 충돌은 승인된 최신 동작과 다른 세션의 변경을 보존하며 해결한다. 통합 기준, 작업 커밋, 검토 결과, 로컬 포트를 진행 기록에 남긴다. 워크트리 정리 시 세션·미커밋 변경·미통합 커밋·실행 서버를 확인하고 강제 삭제를 기본값으로 사용하지 않는다.
