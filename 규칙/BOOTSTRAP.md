# 명정보 홈페이지 세션 부트스트랩 규칙

부트스트랩은 새로운 PM·구현·검토·janiter 세션이 안전하게 작업을 시작하기 위한 공통 절차다. 별도의 CSS Bootstrap 프레임워크 설치를 의미하지 않는다. 이번 규칙은 의존성이나 외부 서비스를 추가하지 않는다.

## 1 역할과 문서 확인

`규칙/README.md`, `WEBSITE_WORK_RULES.md`, `WORKTREE_STRUCTURE.md`를 먼저 읽는다. 진행·인계 기록과 이번 작업 지시를 대조한다. PM은 한 명으로 유지하고 사용자의 핸드오프가 있으면 수신 PM이 역할을 이어받는다. 작업 세션이 독자적으로 통합 기준이나 다른 세션의 범위를 변경하지 않는다.

작업 지시에는 역할, 대상 워크트리, 기준 커밋, 허용 파일, 금지 사항, 완료 기준, 검증 방법이 있어야 한다. 미확정 제품 정보는 임시 표기로 진행할 수 있다. 잘못된 브랜치나 타인의 미커밋 변경처럼 작업 정확성에 영향을 주는 문제는 해결한 뒤 수정한다.

## 2 오르카와 작업 공간 확인

설치된 `orca-cli` 및 필요 시 `orchestration` 스킬의 실행 파일 선택 규칙을 따른다. 해당 실행 파일의 버전별 가이드를 읽고 같은 실행 파일을 계속 사용한다. 다른 에이전트의 결과를 받을 작업은 오르카 orchestration으로 배정하고, 전체 핸드오프는 orca-cli 절차를 따른다.

실제 경로와 브랜치를 확인한다.

```powershell
Get-Location
git branch --show-current
git status --short
git log -3 --oneline
```

오르카의 현재 워크트리 정보와 비교하고, PM이 지정한 기준 커밋이 현재 HEAD의 조상인지 `git merge-base --is-ancestor <기준커밋> HEAD`로 확인한다. 종료 코드 0은 포함, 1은 미포함이며 그 외는 오류다. 기준이 없다면 PM에게 확인한다. 다른 작업자의 변경을 reset·clean·강제 checkout으로 없애지 않는다.

별도 워크트리는 오르카를 통해 만든다. 과거의 터미널 핸들은 재시작 후 유효하지 않을 수 있으므로 실제 목록에서 다시 확인한다. 작업 세션과 통신할 때는 supervised dispatch가 있으면 해당 mailbox를 사용한다.

## 3 실행 환경 확인

```powershell
Get-Content -LiteralPath package.json -Encoding utf8
Get-Command node,npm -ErrorAction SilentlyContinue
```

Node가 있다면 버전과 프로젝트 명령을 확인한다. 현재 기본 스크립트는 `npm run build`, `npm start`다. 통합 시안의 직접 생성은 해당 파일이 존재하는 워크트리에서 `node integrated-site.mjs`로 수행할 수 있다. 파일 존재와 빌드 연결을 먼저 확인한다.

PATH에 Node가 없다면 설치를 임의로 반복하지 않는다. 기존 세션이 사용한 오르카 내장 런타임의 실제 경로·버전과 지원 여부를 확인한 경우에만 세션 범위에서 사용한다. `ELECTRON_RUN_AS_NODE`를 사용했다면 실행 뒤 원래 환경을 복원한다. 이전 보고의 런타임 경로나 버전을 하드코딩해 가정하지 않는다. 패키지는 의존성이 없거나 변경되지 않았으면 재설치하지 않는다.

로컬 서버는 오르카 포트 조회와 실행 상태를 먼저 확인한다. 기존 `4190` 서버는 이전 PM 시안용이며 재사용 전 응답과 제공 워크트리를 확인한다. 별도 서버가 필요하면 사용하지 않는 포트를 선택해 기록하고 기존 서버를 중단하지 않는다.

## 4 작업과 자산 규칙

- 지정된 파일만 수정하고 공통 파일 충돌은 PM과 조정한다.
- 이미지 원본은 `assets/images/`에서 관리한다. 화면에서 사용하려면 빌드 복사 경로와 HTML 참조를 연결한다. 폴더에 저장한 것만으로 웹에 표시되지는 않는다.
- 자산의 파일명, 출처, 권리 또는 사용자 제공 여부, 사용 화면을 기록한다. 확인되지 않은 실제 제품·시설·실적을 사진이나 문구로 주장하지 않는다.
- `janiter`는 실제 참조를 조사하고 정리 목록과 영향을 먼저 기록한다. 일괄 삭제, 타 세션 종료, Git 이력 변경은 기본 정리 작업에 포함하지 않는다.
- 무료 도구와 로컬 미리보기만 사용한다. 문의·결제는 시연이며 실제 전송·결제 연동을 추가하지 않는다.

## 5 검증과 완료 보고

변경된 모듈의 구문·import, 필요한 빌드, 링크·이미지 및 관련 UI를 확인한다. 브라우저 작업 전 해당 브라우저 스킬을 읽는다. PC와 모바일에서 가로 넘침, 주요 메뉴, 키보드 접근, 제품 필터, FAQ, 문의·결제 시연 중 변경 영향이 있는 항목을 검증한다. 문서 변경만 있을 때는 링크·내용·diff 검사로 충분하다.

작업 세션은 변경 파일, 커밋, 수행한 검증과 결과, 미확정 항목, 차단 사항을 PM에게 보고한다. 완료하지 않은 검증은 통과로 기록하지 않는다. PM은 교차 검토 후 통합 결과를 다시 검증한다.

커밋 전 `git diff --check`와 포함 파일 목록을 확인하고 필요한 경로만 stage한다. Git 작성자 설정이 없으면 다른 사람의 신원을 추정하지 않는다. 기존 문서 작업은 일회성 `Codex <codex@localhost>`를 사용했으며 전역 설정을 변경하지 않았다.

## 6 중단과 핸드오프

현재 브랜치·기준 커밋·작업 커밋·미커밋 변경, 검증 결과, 다음 작업, 서버 포트 및 오르카 식별자를 `규칙/`에 남긴다. 기록만으로 실제 에이전트에 인계된 것으로 간주하지 않는다. 전체 인계는 수신 세션의 프롬프트 전달 영수증까지 확인한 뒤 원래 PM이 작업을 종료한다.
